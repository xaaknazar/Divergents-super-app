# ADR: компонент владеет своим внешним видом

**Status:** Accepted (правила явно заданы пользователем; миграция не завершена)
**Date:** 2026-10-07
**Deciders:** владелец Divergents

## Context

В React Native один `style` одновременно управлял размещением и косметикой.
Кнопки и секции собирались из внутреннего оформления и переопределений на экранах.
Условие: сохранить поведение, пять вкладок, обе темы, доступность и текущие пользовательские правки.

## Decision

- Визуальные компоненты находятся плоско в `src/components/`.
- API — явные семантические варианты. Нельзя передавать `style`, `className`, произвольные цвета, радиусы или набор нативных props через spread.
- `Wrapper` владеет только размещением. Внешние padding/margin не заменяют внутренние отступы кнопки или карточки.
- Native `View/Text/Pressable` могут иметь приватные стили **внутри** компонента. Запрет не распространяется на механизм реализации стилей, только на публичное переопределение.
- Экраны хранят состояние, загрузку и обработчики; отображение собирают из компонентов. Callback не должен получить дополнительные побочные эффекты из-за переноса UI.
- Темы и персонализация остаются в существующем ThemeContext. Цвет не вычисляется экраном для передачи дочернему компоненту.
- Каждый перенесённый компонент получает реальные React Native Storybook stories. Данные изолированы от Clerk/API и пользовательских сохранённых настроек.
- Storybook включается только явно в development; production собирает обычное приложение. Это библиотека разработки, не раздел пользовательского приложения.

## Options Considered

### A: сохранить универсальные style overrides

Низкая стоимость миграции, но граница косметики не защищена. Сложнее проверять темы и состояния. Отклонено согласно запросу.

### B: семантические компоненты и отдельный Wrapper

Выбрано. Больше JSX и wrapper-узлов, зато одна точка изменения внешнего вида и ограниченный проверяемый API.

### C: заменить систему сторонним UI-kit целиком

Высокая стоимость, риск изменения поведения и нативных интеграций. Не требуется: существующие токены и компоненты можно сохранить и дисциплинировать.

## Consequences

- Дополнительные контейнеры нужно проверять в списках, flex-разметке и accessibility tree.
- Сначала меняется компонент и все его call sites; старый override API не оставляется для совместимости.
- Семантические варианты нельзя превращать в словарь произвольных CSS/RN свойств.
- Полный статус виден через `npm run ui:audit`; `--check` не пропускает оставшиеся нарушения по whitelist.
- Прохождение typecheck/tests не заменяет нативную визуальную проверку.

## Action Items

1. [x] Button / Wrapper и миграция всех старых кнопок.
2. [x] ProgressBar, ListSection, ListRow; отдельные SectionHeader, Segmented, Chip.
3. [x] Базовый Storybook и изолированная тема.
   - [x] Screen и навигационные шапки: закрытые API поверхностей.
   - [x] Главная обучения: отдельные карточки, полка, каталог, приветствие, ярлыки.
   - [x] Состояния loading/empty/error: семантические компоненты без override API.
4. [ ] Остальные atoms и составные компоненты; полное покрытие stories.
5. [ ] Последовательно все экраны, включая локальные компоненты и нативные поля.
6. [ ] Нативная проверка всех состояний и размеров iOS/Android.
7. [ ] Выбор визуального макета до глобального изменения внешнего вида.
