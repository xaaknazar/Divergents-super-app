# Reading — защита времени при возврате в приложение и два устройства

25 октября 2026. Исправление кода по запросу владельца; **не опубликовано**.
База рабочей ветки: `reading-individual`; в ходе работы отдельным коммитом
`312e245` сохранено ранее подготовленное правило пяти дней. Его изменения
не отменялись. Номер сборки не менялся, production и результаты участников
в этой задаче не изменялись.

## Дефект и воспроизведение

В 99 `bootId` был календарным `KERN_BOOTTIME`. Изменение часов или ошибка
чтения сравнивались с перезагрузкой. При первом непрерывном подходе
`pauseLocked` сохранял `accumulatedMs=0`, теряя текущий измеренный отрезок.
Ранее воспроизведено: 58 минут → 2 минуты до цели → 0 сохранённого времени.
Это подтверждённый дефект, но не доказательство конкретной причины всех
сбоев Fariza: её нативная трассировка не получена.

## Исправления

### Часы и журнал

- Удалено сравнение календарного boot time. `mach_continuous_time` остаётся
  источником длительности и включает сон устройства.
- Признак загрузки — случайный идентификатор в kernel-owned POSIX shared
  memory с именем App Group. Этот объект не зависит от часов, переживает
  завершение процесса и исчезает при перезагрузке системы. Вызовы защищены
  существующим межпроцессным `reading.lock`; имя короткое, QA отделена от
  production. На выходе из аккаунта и при сохранении результата объект не
  удаляется. Новых entitlements нет.
- `ReadingBootMarker.h` — типизированная C-обёртка публичного `shm_open`:
  Swift не вызывает вариативные C-функции напрямую. Header подключён к pod,
  QA и обоим production-расширениям через Expo plugin, включая повторный
  prebuild уже существующих extension-targets.
- Journal хранит максимальное измеренное время и непрерывную временную
  отметку. Во время наблюдения сохраняется контрольная точка не чаще раза
  в пять секунд. Пауза/завершение сохраняют точное измерение.
- При доказанной смене boot marker или уменьшении непрерывного uptime
  сохраняется контрольная точка, а не ноль. Непроверяемый промежуток после
  перезагрузки не начисляется по календарным часам.
- Ошибка доступа к marker не называется доказанной перезагрузкой:
  подход безопасно закрывается с последним сохранённым измерением и
  `revoked`, защита снимается. Неподтверждённое время не добавляется.
- Старые журналы читаются. Календарный идентификатор мигрирует при первом
  валидном наблюдении/возобновлении; уже закрытые данные не переписываются.
  Для старого журнала невозможно задним числом получить отсутствующий boot
  marker: если реальная перезагрузка произошла до миграции и новый uptime
  уже превысил старый, одного legacy-журнала недостаточно, чтобы доказать её.
- `snapshot` возвращает `measuredElapsedMs` вместе со статусом, владельцем,
  идентификатором и поколением из одной критической секции. JS больше не
  соединяет такой снимок с отдельным более поздним чтением остатка. Старые
  native-бинарники/Android сохраняют прежний совместимый fallback.

Контрольные точки не означают выполнение JS в фоне каждую секунду.
Пока приложение приостановлено, длительность вычисляется по непрерывным
часам при следующем чтении. Если устройство реально перезагрузилось до
следующего измерения, восстановить неизмеренный отрезок достоверно нельзя.

### iPad ↔ iPhone

- При активном серверном подходе другого installation ID показывается
  «Чтение идёт на другом устройстве» и инструкция сохранить страницы там.
- Вместо фиктивного 60:00 скрыты локальный таймер, старт и закрытие
  прерванного подхода. История, результаты и рейтинг доступны.
- Неизвестный/нечитаемый installation ID не считается доказанным владельцем
  таймера. Recovery доступно только при точном совпадении ID.
- Локальный активный таймер не переносится на второе устройство. Никаких
  stop/report/reset для чужого device ID не создаётся.
- Для состояния добавлен Storybook `Reading/Challenge/OtherDevice`.

## Осталось перед выпуском

Владелец ответил «Сейчас не могу» на физическую проверку. Новую QA на
телефон не устанавливали. Важно проверить App Group IPC именно в sandbox
физического iPhone/iPad, а также во вновь запущенном процессе Live Activity.
Успех Mac-теста/компиляции не подменяет эту проверку.

1. Отдельная QA: старт → блокировка экрана → возврат; время не прыгает.
2. На карточке: пауза → возобновление → пауза; цифры и shield согласованы.
3. На тестовом устройстве: изменение календарного времени не обнуляет
   измерение; реальная перезагрузка сохраняет последнюю контрольную точку.
4. Два устройства: активный таймер остаётся на первом, на втором notice;
   после сохранения страниц результаты обновляются на обоих.
5. Новая iOS-сборка с native-изменениями. OTA/серверный деплой не исправит
   уже установленный бинарник 99. TestFlight/App Store в этой задаче не запускались.

## Основание выбора платформенного механизма

- [Apple: App Groups Entitlement](https://developer.apple.com/documentation/BundleResources/Entitlements/com.apple.security.application-groups)
  — IPC и формат имён shared memory для группы.
- [Apple: shm_open(2)](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/shm_open.2.html)
  — объект сохраняется между процессами, но не между перезагрузками.
- [Apple XNU: clock.c](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/clock.c)
  — календарное время загрузки корректируется вместе с календарными часами.
