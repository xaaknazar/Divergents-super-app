## Найдено и исправлено

### 1. Сеть удерживала блокировку локального журнала

`ReadingOutbox.flush()` держал общую очередь операций до ответа сервера.
В воспроизведении введённые страницы не записывались на диск, пока зависшая
отправка не завершалась. Завершение приложения в этот момент могло потерять ввод.

- Общая блокировка теперь охватывает только чтение/изменение/запись журнала.
- Отправка упорядочена отдельно для каждого аккаунта.
- Подтверждение перечитывает актуальный журнал и удаляет только подтверждённую
  операцию, сохраняя добавленные за время запроса страницы и другие аккаунты.
- `enqueueMany` сохраняет stop + report одной записью. Конфликт или ошибка
  записи не оставляют наполовину добавленную пару.
- Стабильные operation ID, неизменность payload и повтор после потери ответа
  сохранены. Смена аккаунта не разрешает отправлять или стирать чужие данные.

### 2. Сохранение подхода могло стать незаметным no-op

Фоновый refresh занимал `run()`, и следующий `report()` молча возвращался.
Тест воспроизвёл: finish с 900 000 мс выполнен, пользователь отправил 15 страниц,
но очередь пуста до ответа сервера.

- Сохранение страниц имеет собственную защиту от повторного нажатия и не
  зависит от занятости сети; сначала сохраняет точный результат локально.
- Ошибки snapshot теперь отображаются, а не уходят в необработанный Promise.
- Значения страниц проверяются до закрытия таймера и попадания в очередь.
- Отчёт привязан к конкретному ID подхода: сменившийся сеанс не получает чужие страницы.

### 3. Автоматическое закрытие могло отправить нулевые данные

Два воспроизведённых сценария:

- Нативный start записал реальный сеанс, но ответ мосту потерялся. Старый catch
  отправлял stop(0) + report(0), несмотря на работающий таймер.
- Пользователь открыл recovery, а сервер уже перевёл подход в awaiting_pages.
  Старый обработчик всё равно отправлял report(0).

Теперь неоднозначный запуск перечитывает журнал: существующее время сохраняется,
нечитаемый журнал не означает «времени нет». Отмена пустой серверной резервации
разрешена только при подтверждённом отсутствии локального сеанса. Recovery
проверяет тот же ID, принадлежность устройству, состояние running и повторно
читает журнал после сетевого ожидания. Для awaiting_pages предлагается ввод страниц.

### 4. Поздний snapshot мог вернуть состояние до нажатия кнопки

Общий Promise чтения переиспользовался даже после start/pause/resume/finish/
acknowledge. Пять тестов воспроизвели получение старого ответа вместо нового.

Мост отслеживает ревизию локальных изменений, инвалидирует чтения до и после
команды (включая неясный результат ошибки) и перечитывает устаревший ответ.
Завершение старого Promise не очищает новое активное чтение. Локальные команды
не ждут старый poll; объединение одновременных обычных чтений сохранено.

### 5. Секундный tick повторял сетевую отправку при ошибке

Закрытый локальный таймер при server.status=running запускал синхронизацию
каждую секунду. Теперь есть одна немедленная попытка на переход состояния;
дальнейшие повторы идут через существующие 30-секундный цикл, возврат в
приложение или ручной повтор. Показ времени продолжает обновляться раз в секунду.

### 6. Необязательный checkpoint мог прервать исправный таймер

При ошибке записи промежуточного high-water mark snapshot снимал ограничения,
хотя старый running-журнал был исправен. Следующее измерение могло включить
промежуток уже без защиты.

Ошибка только этой промежуточной записи теперь фиксируется в native trace,
не меняет состояние/защиту и повторяется при следующем чтении. Старый журнал и
монотонный anchor остаются валидными. Ошибки обязательной записи start/pause/
finish **не** скрываются; это отдельные критические переходы. Swift-регрессия
проверяет неудачный checkpoint, сохранность старой записи и последующее точное
измерение без потери времени.

### 7. UI отключал локальные кнопки из-за фонового запроса

Resume, открытие формы и сохранение страниц использовали общий busy сети.
Добавлено отдельное состояние `localBusy`: локальные действия доступны во время
refresh, но блокируются от повторов во время собственного перехода/сохранения.
Пауза остаётся доступной без сети. Старт нового подхода всё ещё требует серверного
подтверждения; при непереданных страницах новый таймер не разрешён.

В Storybook добавлены `Reading/Challenge/SyncingPaused` и `SyncingPages`;
`Saving` отражает настоящее локальное сохранение. Размещение и внешний дизайн
блоков не менялись. Рендер-тест проверяет доступность кнопок при refresh и запрет
повторного сохранения при localBusy.

## Границы проверки и выпуск

Это локальные проверки, не доказательство отсутствия всех ошибок на устройствах.
Новый физический сценарий iPhone/iPad не выполнялся: владелец ранее сообщил,
что сейчас не может проверить QA. App Group IPC на iOS, реальная блокировка,
Live Activity и переход между двумя устройствами остаются физическими release-
проверками из предыдущего отчёта. Android native-сборка в этом аудите не собиралась;
общие TypeScript-пути проверены тестами, нативный build — iOS.

Нужна новая мобильная сборка с native-изменениями: серверный деплой не обновит
установленный таймер. Полного release archive, подписи и TestFlight-публикации
в этой задаче не было. Коммиты, сервер и реальные результаты не изменялись.
