# Reading: недоступный старт и ожидание сервера

24 октября 2026. Диагностика по запросу владельца, **без исправления протокола и без публикации**.

## Вывод

Сообщение «Нет подтверждения сервера…» не определяет причину. `readingErrorMessage` показывает его также для неизвестной ошибки или ошибки проверки JSON, а не только при отсутствии интернета. Конкретный инцидент участника пока не атрибутирован: не предоставлены псевдоним, сборка и время, доступ по текущему SSH-ключу отклонён. Текущие нагрузка production и журналы не проверены; считать нехватку RAM причиной нельзя.

В мобильном коде воспроизведены три независимые проблемы. Напоминание о страницах улучшает понятность, но само по себе их не устраняет.

## Воспроизведено изолированными тестами

Тесты не обращались к API и не меняли участников. Использованы настоящий `useReadingChallenge` / `ReadingOutbox`, подставные сеть, диск и нативный модуль.

1. **Потерян ответ успешного старта.** Сервер создал `running`-сеанс; POST завершился ошибкой транспорта. Команда осталась в очереди. Повтор получил подтверждение и очистил очередь, но `readingNative.start` не был вызван; состояние стало `needsRecovery=true`, новый старт заблокирован. Повтор синхронизации не завершает двухэтапный запуск. Аналогичная уязвимая граница находится между успешным POST и следующим detail GET, до блока native-start recovery.
2. **Сеть занимает очередь записи на диск.** `flush` удерживает общий `journalTail` во время `await send`. Независимый `enqueue`, в том числе другого аккаунта, не сохраняет команду до окончания чужого сетевого запроса. После ответа запись завершается. Защита от конкурентной перезаписи нужна, но сетевое ожидание внутри неё не нужно.
3. **Фоновая синхронизация блокирует действие Start.** При ожидающем detail GET `busy=true`; вызов `start` молча возвращается без запроса. Кнопка интерфейса также disabled при loading. Этот же `run(synchronize)` вызывается периодически каждые 30 секунд при активном приложении.

Результат: **3/3 диагностических теста**. Они подтверждают текущее нежелательное поведение, а не успешное исправление. Материалы временного аудита: `/tmp/divergents-reading-reliability-audit.nywBUD/reliability.test.tsx`, `results.log`.

## Причины задержек, подтверждённые кодом

- `src/state/useReadingChallenge.ts`, Start: `synchronize` с полным GET → POST start → ещё один полный GET → native start. При наличии очереди запросов больше. Ответ POST уже содержит sessionId, budgetMs, serverNow, dayEnd, но быстрый путь на нём не построен.
- `src/data/reading.ts`: `timeoutMs=12000`, `retries=0` и для GET, и для POST. Быстрого повтора при единичном транспортном обрыве нет; экран повторяет общий sync через 30 секунд только пока смонтирован и приложение активно.
- `src/state/readingOutbox.ts`: любой нераспознанный отказ `stop/report` остаётся в начале последовательной очереди. Это сохраняет доказательства, но без отдельного разрешения конфликта способно блокировать следующие команды.
- В локальном серверном исходнике `/private/tmp/divergents-reading-reset-code.C7EDvl/source/lib/reading-service.ts` detail читает всех участников, все дневные записи челленджа и пересчитывает полный рейтинг. Это лишняя работа для управления одним таймером.
- В том же серверном исходнике каждое новое обычное действие после персонального lock получает `FOR UPDATE` общей строки ReadingChallenge. Записи разных участников одного челленджа сериализуются. Это потенциальный источник задержек под нагрузкой; фактические ожидания production не измерены.

## Приоритет исправлений

### P0 — восстановимый старт и доступные кнопки

- Сохранять отдельное состояние `pending_start` до POST. Использовать тот же operationId/sessionId для получения квитанции, а не создавать новый запрос.
- При неопределённом исходе проверять существующий сеанс/квитанцию. Предлагать «Продолжить запуск» только на исходном устройстве и по явному нажатию пользователя; не включать блокировку из фонового retry.
- Не запускать таймер до подтверждения сервера; не засчитывать время до фактического нативного старта. Чужой или уже закрытый сеанс не возобновлять.
- Разделить `refreshing`, `starting`, `savingPages`, `preparingProtection`. Фоновое обновление рейтинга не должно делать нажатия пользователя молчаливыми no-op. Двойной start всё равно должен быть исключён.

### P0 — надёжная очередь

- Короткая сериализация только чтения/изменения локального журнала. Сеть — вне неё; один отправитель с сохранённым порядком stop → report и безопасным подтверждением конкретного operationId без потери новых записей.
- Разделить временные ошибки, авторизацию и постоянные конфликты. Конфликт нельзя удалять как «успешный» или бесконечно считать отсутствием интернета.
- Ограниченные повторные отправки с тем же ключом, увеличивающейся случайной задержкой и учётом `Retry-After`. Не повторять бездумно постоянные 4xx. Повтор при восстановлении связи/возврате в приложение.

### P1 — быстрый личный API

- Лёгкий ответ для собственного таймера, дневной цели и несохранённого подхода. Рейтинг и историю загружать отдельно.
- Достаточная квитанция POST start для безопасного запуска: добавить оставшуюся личную цель к имеющимся полям, исключить обязательный последующий полный detail.
- Сузить серверные блокировки после проверки конкурентных сценариев; не просто убрать все locks. Сохранить уникальность сеанса, квитанции, согласованность закрытия дня и изменений правил.

### P1 — диагностика и приёмка

- Сквозные requestId / operationId, HTTP status, код ошибки, длительность авторизации/API/БД/native и возраст старейшей команды. Без токенов, книги и персональных данных в общих логах.
- UI: отдельно «Запускаем», «Сохранено на телефоне, отправляем», «Нужно сохранить страницы», «Нужно войти заново», «Конфликт подхода».
- Прогон: потерян POST-ответ, потерян следующий GET, повтор после перезапуска, 401/409/429/503, долгий ответ, восстановление сети, два устройства, полночь, старые сборки. Данные не теряются, время не удваивается, блокировка всегда снимается локальной паузой.
- Измерять p50/p95/p99 времени старта и подтверждения страниц отдельно от общего health; сравнивать одинаковые запросы/нагрузку до и после. Численного ускорения без замеров не обещать.

## Основание подхода

Рекомендации по ограниченным повторам, backoff/jitter и неизменному идентификатору операции согласуются с [AWS Builders’ Library: timeouts and retries](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) и [idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/). Идемпотентные серверные квитанции уже есть — их нужно правильно использовать в восстановлении мобильного запуска.

Сначала исправляется протокол и измеряется результат. Увеличение сервера не устранит подтверждённые клиентские сценарии зависшего старта и общей очереди.
