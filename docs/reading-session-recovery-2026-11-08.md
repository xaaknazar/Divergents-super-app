Sunny, сборка 118, iOS 18.7.8 (со слов владельца): экран сообщает о подходе другого челленджа, повторное вступление не помогает.
Проверка production выполнена только SELECT в READ ONLY транзакции с ROLLBACK: сейчас Extreme approved, Moderate left; несколько выходов/повторных вступлений; все семь серверных подходов помечены day=0, reported/rejected после пользовательского выхода. ## Воспроизведение и причина

В сборке 118 и до исправления pause оставляет resumeVersion=1, terminal=false. Нативный acknowledge разрешает удалять только paused + terminal=true. Выход из челленджа вызывал pause, затем acknowledge: серверный выход мог завершиться, но телефон сохранял незавершённый журнал.
Восстановление проверяло reportedSessionIds только для уже terminal-сеансов. Поэтому подтверждённый сервером закрытый подход на обычной паузе (либо ещё running) навсегда блокировал новый таймер. Несовпадение sessionId ошибочно называлось другим челленджем без проверки принадлежности.
Два теста воспроизвели этот дефект до правки (paused/running).

## Исправление

- После подтверждённого выхода/смены участия/окончательного отказа сервера локальный подход сначала запечатывается через существующий finish с accountId, sessionId и generation, затем acknowledge.
- После выхода generation перечитывается: предварительная пауза могла изменить её.
- Свежий ответ сервера с конкретным reportedSessionId освобождает также мягкую паузу/running остаток. Отсутствия session в ответе недостаточно. Кэш без сети не используется как новое доказательство закрытия.
- Нет повторной отправки минут или страниц при очистке закрытого журнала.
- При неизвестном подходе, другом аккаунте, изменившейся generation или ошибке завершения журнал сохраняется; новый старт остаётся заблокирован.
- Сообщение больше не утверждает, что неизвестный подход обязательно принадлежит другому челленджу.
- Нативные исходники и сервер не изменены.
