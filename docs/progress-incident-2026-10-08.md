## Подтверждённый дефект

1. В архиве сборки 85 (`5966ae64-7f9f-40e4-853c-f63d37cf6a5a`) уже есть строгий
   протокол v2: операция, день, ожидаемая версия, обязательная квитанция.
   Проверен сохранённый EAS archive в `/tmp/divergents-release85-inspect.H18ifk/archive`.
   SHA256 исходного `progressOutbox.ts`: `2718a0c9e1f69568e6cc272e71822d7ca346ff4f448c090fd4ce09622f414f57`.
2. Production alias при проверке всё ещё указывал на
   `dpl_6j8SdcdeptHCZLLNRR721mW6FsaD`, `divergents-qg8e3fzfj-xaknazars-projects.vercel.app`,
   созданный 7 октября, 11:26 Алматы. Его исходная ревизия `8be86de` содержит v1:
   сервер не учитывает operationId/expectedVersion/day и возвращает старое подтверждение.
3. Мобильный клиент считает этот HTTP 200 некорректной квитанцией. Старая очередь
   снова выбирает первую задачу, делает общую паузу и не доходит до остальных.
   Поэтому часть значений может быть записана, но оставаться «неподтверждённой»,
   а другие задачи — вообще не отправлены.
4. Карточка показывала «Готово» по локальному оптимистичному значению, а не квитанции.

Регрессионные тесты сначала воспроизвели ошибку; после изменений проходят.
Это не доказательство нехватки CPU/RAM. В ограниченной выборке последних 100 POST
по запросу логов `/progress` за 24 часа было 93 HTTP 200, 6 HTTP 409, 1 HTTP 405.
Это не полный аудит нагрузки, не исключительно мобильные отметки и не проверка
конкретных пострадавших. HTTP 200 сам по себе не доказывает корректность протокола.

## Что изменено

- `progressOutbox.ts`: отдельный backoff для каждой операции; порядок правок одной
  задачи сохранён, независимые задачи не блокируются. Попытка не меняет ID/payload.
- Ошибка ответа не маскируется под отсутствие сети или сбой локального диска.
  Успех соседней задачи не скрывает оставшуюся ошибку.
- «Готово» и зелёный итоговый индикатор требуют подтверждения. При очереди/ошибке
  показывается ожидание; закрытие дня не скрывает неподтверждённые отметки.
- Серверная часть: см. `divergents-lms/docs/progress-rollout-2026-10-08.md`.
- `release:check` и EAS pre-install hook проверяют read-only capabilities endpoint
  рабочего API. HTTP 404/405/503, редирект, таймаут или неполный контракт останавливают
  release-сборку. До публикации серверного исправления endpoint возвращал 405;
  9 октября проверка рабочего API успешно пройдена перед сборкой 86.
  Development-профили исключены, preview/production — нет.
  Это защита при сборке, не гарантия от последующего отката сервера; перед submit
  проверку нужно повторить. Для custom EAS builds hook надо включать явно.

divergents-lms/docs/progress-release-2026-10-09.md.

## Эксплуатация до выпуска

Проверять фактический результат через сайт. Не удалять приложение и его данные:
очередь неподтверждённых операций хранится на устройстве. Не переносить автоматически
вчерашние значения на сегодня. Восстановление прошлых дней — только после сверки
участников/дат/значений и отдельного подтверждения владельца.

## Профессиональные практики

- [AWS: безопасные повторы с idempotency token](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/):
  один запрос — одна идентичность, сохранение результата и повтор квитанции;
  смена payload не должна незаметно считаться повтором.
- [Android: offline-first data layer](https://developer.android.com/topic/architecture/data-layer/offline-first):
  устойчивая локальная очередь, повтор с задержкой, отдельное разрешение конфликтов.
- [Expo: build lifecycle hooks](https://docs.expo.dev/build-reference/npm-hooks/):
  автоматическая проверка совместимости перед release-сборкой.

Эти меры не обещают невозможных «100% без сбоев»: они сохраняют намерение,
предотвращают тихую перезапись и позволяют отличать локальный ввод от записи на сервере.
